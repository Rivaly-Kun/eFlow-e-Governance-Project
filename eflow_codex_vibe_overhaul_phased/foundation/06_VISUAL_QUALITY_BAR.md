# Visual Quality Bar

## Reference

The main visual/product reference is monday.com's work-management experience.

The goal is not a pixel-for-pixel clone.

The goal is to achieve the same class of:
- productivity
- density
- speed
- hierarchy
- work visibility
- interaction quality

## Avoid generic dashboard design

Do not default every page to:

Header
→ five KPI cards
→ charts
→ card grid

That is not the eFlow identity.

## Preferred product language

Use:
- workspace headers
- tabs/views
- toolbars
- grouped tables
- compact rows
- owner/avatar columns
- strong status cells
- due date cells
- priority
- searchable/filterable views
- contextual menus
- side panels
- sticky controls
- horizontal work canvases where useful

## Canvas use

Desktop productivity applications may use wide horizontal space.

Do not over-center content inside a narrow max-width page when a table/workspace benefits from width.

## Density

Use deliberate productivity density.

## Status

Status should be highly scannable.

Use real semantic color plus text.

Do not rely on color alone.

## Cards

Cards are allowed, but work rows/tables should dominate operational pages.

Use cards for:
- summaries
- side context
- grouped supporting information
- empty/attention states

Do not wrap every row and every section in a separate card.

## Creativity

Codex should actively improve:
- composition
- spacing
- typography
- interaction
- toolbar behavior
- group visuals
- hover/focus states
- responsive adaptation
- empty states
- microcopy

A technically correct wireframe is not accepted as finished UI.

## Screenshot review gate

Every major phase that changes visible UX must provide or request visual review before moving on.

Passing TypeScript/tests/build is necessary, not sufficient.
